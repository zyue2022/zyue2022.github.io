Java中Stream流完全指南

Stream 是 Java 8 引入的一套集合处理 API。它让你用”声明式”的方式处理数据——你告诉它”要什么”，而不是”怎么循环”。这篇文章把 Stream 的用法、原理、收集器、并行流、常见坑都过一遍，争取让你看完能直接上手写，也知道哪里会翻车。

一、Stream 到底是什么

先说清楚它不是什么：

  • 不是集合，不存储数据，只是数据的”管道”。
  • 不是数据结构，没有下标，不能随机访问。
  • 不会修改源数据，所有操作都产生新结果。

两个关键特性必须记住：

  1. 惰性求值：中间操作（filter、map 等）不会立刻执行，只有遇到终止操作（collect、count）才会真正跑一遍。
  2. 一次性消费：一个 Stream 对象只能被终止操作消费一次，用完就废了，再调用会抛 IllegalStateException: stream has already been operated upon or closed。

关于第三个重载的 combiner：串行执行时它不参与计算；一旦 .parallel()，流会被切成多段，每段各自用 accumulator 算出局部结果，最后用 combiner 把各段结果合成一个。所以 combiner 不是装饰，是并行正确性的保证。

必须规避的陷阱：初始值（identity）必须是”中性值”，即满足 combiner.apply(identity, x) == x。求和用 0、求积用 1、拼接用 ""。如果求和误把初始值写成 10，并行时每个分片都从 10 起步，合并后会多出”分片数个 10”，结果就错了。

reduce 与 collect 的分工：reduce 适合”聚合成一个标量或简单对象”（数字、字符串、自定义累加器）；”收集成集合 / 分组 / 转 Map”请用 collect + Collectors，那是它的主场，别硬用 reduce 拼 List（既慢又啰嗦）。

七、并行流（Parallel Stream）

一行 parallel() 就能把串行流变成并行：

原理：底层用 ForkJoinPool.commonPool()，把数据分片，多个线程各自处理一段，最后合并。

什么时候适合上并行：

  • 数据量大（万级、百万级以上才看得出收益）。
  • 每个元素的计算是 CPU 密集 且彼此独立。
  • 中间操作里没有 sorted、distinct、有状态操作这种需要”碰头”的（它们会大幅抵消并行优势）。

什么时候千万别用：

  • 数据量小：线程调度开销比计算还大，反而更慢。
  • IO 密集任务（网络、数据库）：会占满公共线程池，拖累整个 JVM。
  • 操作里有共享可变状态：并行读写没加锁会出并发 bug。

踩坑点：findAny 在并行下确实更快（随便给一个），但 findFirst 在并行下要保序，成本更高；如果你不关心顺序，用 findAny。

八、常见坑与注意事项

把这几个坑记住，能省掉不少调试时间。

1. 流只能消费一次

解决办法：每次用都重新 list.stream()，或者把结果先 collect 成集合。

2. 中间操作是惰性的，peek 不触发

3. 自动装箱的性能陷阱

处理大量数值时务必用 IntStream / LongStream / DoubleStream，避免无谓的装箱。

4. 流里改外部变量会编译失败

Stream 的函数式接口要求捕获的变量不可变。要聚合就用 reduce / collect，别想着改外部变量。

5. 流里出现 null 元素

源头可在 map 前先 .filter(Objects::nonNull) 剔除 null 元素。

6. toMap 的重复 key

前面提过，重复 key 默认抛异常，记得传合并函数。

7. forEach 顺序与并行

并行流里 forEach 不保证顺序，forEachOrdered 才保序（但拖慢并行）。想要有序输出，不如直接串行。

九、性能与最佳实践

一些实打实的建议：

  1. 原始类型流优先：处理 int/long/double 用 IntStream 等，避免装箱开销。
  2. 短路操作往前放：filter 尽量放在 map 前面，先减数据量再做转换。
  3. 别在流里搞副作用：流的精髓是”无副作用”——不要在 forEach / peek 里修改外部状态，用 collect / reduce 拿结果。
  4. sorted + 并行要谨慎：大数据量且确实需要排序时，先想清楚是否真要并行。
  5. 不是所有循环都该换 Stream：简单的几行 for 循环、需要中途 break/continue、或者逻辑分支很绕的场景，传统循环反而更清晰。Stream 是让”数据转换”变优雅，不是消灭所有 for。
  6. 可读性第一：一条流水线超过七八步、嵌套了 flatMap 又 groupingBy 的，可以考虑拆成中间变量，或者干脆分步写，别为了”炫”堆成一行。

假设有一个 Order 列表，需求：统计每个用户、每个月的订单总金额，并且只保留金额大于 1000 的记录，最后按金额降序输出。

这个例子串起了 filter → groupingBy(多级) → reducing(下游聚合) → 再 stream 排序输出，基本覆盖了日常 80% 的聚合场景。

十一、总结

Stream 的核心心智模型就三句话：

  • 数据源 + 中间操作（惰性）+ 终止操作（触发） 三段式。
  • 无状态操作（filter/map/flatMap）便宜，有状态操作（distinct/sorted/limit）贵，并行时尤其明显。
  • 能 collect 就别副作用，能原始流就别装箱。

它不会让你写出更快的程序（极端情况下甚至更慢），但能让你写出更短、更易读、更不容易出 bug 的数据处理代码。先把中间操作和 Collectors 那几个常用方法练熟，剩下的 parallel、自定义收集器都是锦上添花，用到再查也不迟。
